## 2. الفكرة العامة للمشروع (Project Overview)
النظام البرمجي المصمم بلغة **#C** يمثل **"نظام إدارة مركز صيانة وإصلاح أجهزة منزلية"** (مثل الثلاجات، الغسالات، والمكيفات).  
يتيح النظام تسجيل الأجهزة بدقة، والتحقق من أرقامها التسلسلية، ومتابعة حالات الصيانة الخاصة بها، بالإضافة إلى حساب التكاليف الإجمالية المتوقعة للمركز ديناميكياً وإطلاق إشعارات فورية عند تحديث بيانات الأجهزة.

## 3. توثيق تطبيق مفاهيم OOP الستة في الكود

### 3.1 التجريد (Abstraction)
تم تطبيق التجريد لفصل واجهة التعامل عن التفاصيل التنفيذية من خلال:
* **الواجهة `IDevice`:** لتعريف الخصائص والدوال الأساسية المفروضة على أي جهاز يدخل المركز.
* **الفئة المجردة `Device`:** فئة أساسية ترث من الواجهة وتضم الصفات المشتركة، وتحتوي على الدالة المجردة `CalculateRepairCost()` التي لا تمتلك جسماً برمجياً، ويُترك أمر تنفيذها للفئات الفرعية.

### 3.2 التغليف (Encapsulation)
تم حماية بيانات الكائنات ومنع الوصول المباشر للحقول من خلال:
* جعل جميع الحقول (`Fields`) خاصة `private` مثل `_serialNumber` و `_baseCost`.
* استخدام الخصائص `Properties` للوصول الآمن للبيانات، مع جعل الخاصية `SerialNumber` و `Model` للقراءة فقط (بدون مفسر `set`) لضمان عدم تعديل البيانات الحساسة بعد إنشاء الكائن.

### 3.3 الوراثة (Inheritance)
تم بناء هيكلية وراثية واضحة لإعادة استخدام الكود وتجنب التكرار:
* إنشاء ثلاث فئات فرعية (`Subclasses`) هي: `Refrigerator` و `WashingMachine` و `AirConditioner`.
* ترث هذه الفئات بالكامل من الفئة الأب `Device` وتستدعي المشيد الأساسي للأب عبر الكلمة المفتاحية `base`.

### 3.4 تعدد الأشكال (Polymorphism)
تم تطبيق تعدد الأشكال بنوعيه لضمان مرونة النظام:
* **تعدد الأشكال الديناميكي (Method Overriding):** قامت كل فئة فرعية بإعادة تعريف الدالة `CalculateRepairCost()` لحساب تكلفة الإصلاح بناءً على معاييرها الخاصة (إضافة تكلفة الغاز للثلاجة، أو قطع التبديل للغسالة، أو سعة التبريد للمكيف).
* **التعامل الموحد (Upcasting):** تم تخزين كائنات الأجهزة المختلفة داخل قائمة موحدة من نوع `List<IDevice>` في فئة الإدارة، وتم استدعاء الدوال ديناميكياً أثناء وقت التشغيل (`Runtime`).

### 3.5 التفويض والأحداث (Delegates & Events)
تم بناء نظام إشعارات ذكي لربط أجزاء النظام دون حدوث اقتران وثيق (`Loose Coupling`):
* تعريف التفويض `MaintenanceStatusHandler` لتحديد بنية التنبيهات النصية.
* إطلاق الحدث `OnStatusChanged` داخل فئة الإدارة فور نجاح دالة `UpdateDeviceStatus` في تعديل حالة أي جهاز، لتنبيه الواجهة الرئيسية بشكل فوري.

### 3.6 الفئات والأعضاء الثابتة (Static Class & Members)
تم عزل ميزات التحقق من البيانات في فئة مستقلة:
* إنشاء الفئة الثابتة `ValidationUtils` والتي لا يمكن بناء كائنات منها.
* تحتوي الفئة على دالة ثابتة `IsValidSerialNumber` للتحقق من تطابق الرقم التسلسلي مع الصيغة المطلوبة (`SN-XXXX`) باستخدام التعبيرات النمطية (`Regex`).

## 4. مخطط العلاقات المبسط (UML Class Diagram)

يصف مخطط العلاقات الهيكلية المطبقة في المشروع كالتالي:

```text
       ┌───────────────┐
       │   «interface» │
       │    IDevice    │
       └───────▲───────┘
               │ (Realization - خط متقطع)
       ┌───────┴───────┐             ┌────────────────────┐
       │ abstract class│             │ MaintenanceManager │
       │    Device     ├────────────►│ ────────────────── │
       └───────▲───────┘ (Aggregation│ - List<IDevice>    │
               │          خط متصل)   └────────────────────┘
   ┌───────────┼───────────┐
   │           │           │ (Inheritance - خطوط متصلة بسهم مجوف)
┌──┴─────────┐┌┴──────────┐┌┴──────────────┐
│Refrigerator││WashingMach││AirConditioner │
└────────────┘└───────────┘└───────────────┘
```

* **علاقة تحقيق (Realization):** ترتبط الفئة `Device` بالواجهة `IDevice`.
* **علاقة وراثة (Generalization):** ترتبط الفئات الثلاث الفرعية بالفئة الأب `Device`.
* **علاقة احتواء (Aggregation):** ترتبط فئة `MaintenanceManager` بالواجهة `IDevice` لإدارة قائمة الأجهزة.
